That confirms it. curl.exe uses the Windows system trust store (schannel) and connected fine with HTTP/1.1 200 OK — so Windows itself already trusts whatever's signing this connection (Zscaler's re-signed cert included). That rules out the network, Zscaler policy, and DNS entirely.

So the root cause is narrowed to exactly one thing: Python's certifi bundle doesn't have the Zscaler root CA that Windows has. requests/grpc/urllib3 in Python ignore the Windows cert store by default and only trust whatever's in certifi's file — which is a fixed list of public CAs and has no path to add Zscaler's internal one automatically.

To nail down the exact gap and fix it:

1. Confirm certifi is the blind spot

powershell
py -c "import certifi; print(certifi.where())"

Open that file in a text editor and search for Zscaler. It won't be there — that's the confirmed cause.

2. Get the Zscaler root cert that Windows trusts, in PEM format

powershell
# Export it straight from the Windows cert store
$cert = Get-ChildItem -Path Cert:\LocalMachine\Root | Where-Object { $_.Subject -like "*Zscaler*" }
$cert | ForEach-Object {
    $path = "C:\Temp\$($_.Thumbprint).cer"
    Export-Certificate -Cert $_ -FilePath $path -Type CERT
}

This dumps the Zscaler root (and intermediate, if listed separately) as .cer files. If Get-ChildItem returns nothing from LocalMachine\Root, check CurrentUser\Root too — Zscaler sometimes installs per-user.

3. Convert to PEM and append to a combined bundle (don't edit certifi's file directly — it gets overwritten on every pip install --upgrade certifi):

powershell
certutil -encode C:\Temp\<thumbprint>.cer C:\Temp\zscaler.pem
py -c "import certifi; print(certifi.where())"   # copy certifi's path
copy "<certifi-path>" C:\Temp\combined-ca-bundle.pem
Get-Content C:\Temp\zscaler.pem | Add-Content C:\Temp\combined-ca-bundle.pem

4. Point Python at the combined bundle

powershell
$env:REQUESTS_CA_BUNDLE = "C:\Temp\combined-ca-bundle.pem"
$env:SSL_CERT_FILE = "C:\Temp\combined-ca-bundle.pem"

Add these two lines to your venv's Activate.ps1 (or your PowerShell profile) so they're set automatically every time, not just this session.

5. Verify the fix

powershell
py -c "import requests; print(requests.get('https://api.platform.opentargets.org').status_code)"

Should print 200 with no SSL error.

Simpler alternative, if you'd rather not hand-manage certs: install pip-system-certs, which patches Python at import time to use the Windows certificate store (same one curl.exe/schannel uses) instead of certifi:

powershell
py -m pip install pip-system-certs

Once installed, no env vars needed — Python automatically trusts whatever Windows trusts, which Step 1 already proved includes Zscaler's cert on this machine. This is usually the fastest fix and the reason it "just works" on other company laptops that happen to have something similar already set up (or that never hit this path because a prior IT image included it).

If pip-system-certs is blocked by policy or can't install (corporate proxy blocking PyPI), fall back to the manual combined-bundle approach in steps 1–4.
